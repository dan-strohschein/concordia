# concordia-studio: agent guide

## Purpose
Agent Studio's harness-neutral source of truth and its engine module: role files, the team, the task board, the Studio journal, and the `task.*` / `studio.*` methods. It never calls an LLM (ADR-0002).

## Public entry points
- `StudioModule`: the engine module (`[studio]` in `concordia.toml` turns it on via `concordia-app`).
- `RoleFile`, `RoleSpec`, `RoleId`: `studio/agents/<role>.md` (YAML frontmatter + Markdown body).
- `RoleColor`: a role's `color`, one of Claude Code's 8 agent colors or any `#rrggbb` (ADR-0083).
- `doctor`: the machine checks (Claude Code and its login, an API key noted, `concordia` on PATH, sync freshness), shared by `studio.doctor`, `concordia studio doctor` and the editor's launcher.
- `SkillFile`, `CLAUDE_SKILL_FIELDS`: `studio/skills/<name>/SKILL.md` (Claude Code's skill format), validated on load and before sync.
- `Team`, `Gate`, `GateParty`: `studio/team.toml`.
- `Roster::load` / `Roster::resolve`: team overrides applied, tool patterns expanded against a `ToolCatalog`.
- `TaskBoard`, `TaskStore`, `Task`: `studio/tasks/T-0001-<slug>.task.md`.
- `StudioJournal`: `.concordia/studio/journal.jsonl` (ADR-0080); hooks append to it directly.
- `default_roster`, `init`: the embedded default team (`roster/`): 12 roles and 12 engine skills.
- `sync`, `SyncOptions`, `SyncReport`: compile the roster to Claude Code files (`claude_code/`).
- `Policy`: who may call which tools, write which paths, run which commands; written by sync to `.claude/concordia/policy.json`, rebuilt from the engine by `concordia mcp`.
- `hook::run`: the `concordia studio hook <event>` logic (pure; the CLI only does stdin/stdout).
- `Slots`: role instance slots shared by `concordia mcp` and the hooks.
- Team questions (ADR-0081): `studio.ask/answer/escalate/questions` (`question_methods.rs`), the board's desk (`task/desk.rs`), and `Question`, derived from the journal (`task/question.rs`). Hook context comes from `team_context.rs`.

## Invariants
- Text files are the source of truth; task history lives only in the Studio journal, never in task files.
- Every board operation holds `.concordia/studio/board.lock` and first syncs with the journal and the files. A file change no journal entry explains is a hand edit, logged as `human:local`.
- Journal writers lock the file, drop an incomplete last line, then append one line. `seq` is the line number.
- Role `mcp_tools` patterns must each match a tool the project offers; path patterns stay inside the project.
- A role's `color` is a Claude Code color name or `#rrggbb`. Agent files always get a Claude Code name (the nearest one, by CIELAB distance), and `studio.roster` returns the editor's hex as `color` and the name as `agent_color`. The default roster's enabled roles have distinct colors.
- `studio.doctor` has editor audience, so it is never an agent tool. The doctor reads only `PATH` and whether `ANTHROPIC_API_KEY` is set, never a credential's value.
- Only gate parties may approve or reject; rejections past `max_attempts_per_task` block the task for a human.
- Sync owns `.claude/agents/*.md` and `.claude/skills/*/SKILL.md` outright: each carries a `# generated by concordia studio sync ...; hash=...` frontmatter line, and a file whose hash no longer matches was edited by hand and is refused without `force`. Files without the marker are never touched or deleted.
- Sync merges `.claude/settings.json`, `.mcp.json` and `CLAUDE.md`: it changes only its own hook handlers (`concordia studio hook ...`), its two `env` keys, `agent`, the `concordia` server and the text between the `concordia-studio` markers, and keeps everything else in order.
- Generated agent frontmatter uses only `CLAUDE_AGENT_FIELDS` and never `hooks`, `mcpServers` or `permissionMode` (they don't load in untrusted `claude -p`). Non-director agents never get the `Agent` tool.
- The hook never starts an engine: it reads only the policy file. PreToolUse fails closed (unreadable input exits 2; a missing or stale policy denies). The other events fail open with a warning.
- Engine calls are stamped with a reserved `_studio` key that only `concordia mcp` reads and strips; engine params never see it.
- Questions are journal entries only (`question_asked`, `question_answered`, `question_escalated`), with no question files. Ids (`Q-0001`) are allocated under the board lock. Only the addressed role, the director or a human may answer, and only a human once escalated. Only the director escalates, which blocks the task as `system:studio`; a human answer moves it back to `todo`. Text caps: 280, 500 and 280 characters.
- Question hooks only add context and never block: SubagentStart (questions for the role, and new answers to its questions), PostToolUse on `Agent` (the director's changes since its last turn) and UserPromptSubmit (new human answers). What each has delivered is kept in `.concordia/studio/cursors.json`.
- The default roster lives only in `roster/`. Its tool scopes name only tools that exist today (M3 refinement G10).
- Tool access is set by the admin in the roster, and only there (ADR-0073). Default roles name each tool, with no globs. Every tool a role has is one its prompt or preloaded skills use, and every tool those tell it to use is in its scope. A skill's `## For the director` section counts only for the director.
- The director coordinates and never inspects the world. It has only task tools, `studio_*` and `txn_history`, and it reviews the evidence specialists attach to tasks.
- There is no budget on the whole tool list. Each enabled default role's tool definitions stay under 50k tokens (`concordia-mcp/tests/role_tool_budget.rs`, ADR-0073; raised from 22k on 2026-11-21 until the schemas are slimmed).
- Every role prompt has the sections Mission, You own, You never, Workflow, How you verify, When to escalate and Output contract (with a fenced example). Enabled roles' prompts name only tools in their scope.
- A role's `skills` must exist in `studio/skills/`. Skill frontmatter uses only `CLAUDE_SKILL_FIELDS`, `name` matches the folder, and description plus `when_to_use` stay within 1,536 chars.
- A default skill that names a tool the engine doesn't offer yet carries a `> **Not available yet:**` line naming those tools and the phase that brings them (tracked in the M3 plan's 3.1, 3.2 and 3.7 follow-ups).

## How to test
`cargo nextest run -p concordia-studio` (role, team, journal, task board and method tests; `insta` snapshots).

## Common tasks
- **Add a default skill:** write `roster/skills/<name>/SKILL.md`, add it to `SKILLS` in `defaults.rs`, preload it in roles' `skills`, and update the list in `tests/skills.rs`.
- **Add a role field:** add it to `RoleSpec` and `ROLE_KEYS`, then extend the round-trip property test.
- **Add a journal event:** add a `JournalEvent` variant (snake_case `kind`), and map it in `task()` and `kind()`.
- **Add a method:** define it in `methods.rs`, add it to `all()`, document it in `docs/guides/agents-engine-api.md` and update the schema snapshot.

## Don'ts
- Don't write task history into `.task.md` files, or Studio events into the per-scene command journal.
- Don't add YAML keys to role files without updating `ROLE_KEYS` (unknown keys are errors by design).
- Don't put personal paths or private game details in the default roster.

## Engineering rules
These apply to every change, by humans and agents alike.
1. **TDD on every phase.** Write the tests first, see them fail, implement, then refactor.
2. **SOLID.** Depend on abstractions at crate boundaries; extend through traits rather than by editing callers.
3. **No duplicate functionality.** Before writing any implementation, search for existing functionality (grep, `cargo doc`, crate `AGENTS.md` files). Extend or refactor what exists; never write a parallel version.
4. **Single responsibility at every level:** function, type, module and crate.
5. **Small functions** that do one thing.
6. **Validate parameters.** Every function checks its inputs:
   - Rust: encode invariants in types (newtypes, enums, `NonZero*`); validate at boundaries and return `Result` with a descriptive error; use `debug_assert!` for internal invariants. Public APIs never panic on bad input.
   - TypeScript: strict types, plus runtime validation at API and IPC boundaries.
7. **Short comments.** One-line doc comments on public items; no essays, and no comments that restate the code.
8. **Idiomatic code.**
   - Rust: follow the Rust API Guidelines and keep it clippy-clean; `thiserror` in libraries, `anyhow` only in binaries and tests.
   - Editor UI: idiomatic React and TypeScript, with function components, hooks, strict mode, ESLint and Prettier.
